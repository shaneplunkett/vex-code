# OpenTelemetry GenAI conventions for Vex Code turns

**Research date:** 22 July 2026

**Question:** Which current OpenTelemetry GenAI semantic conventions should Vex Code adopt for turn, model, agent, tool, token, content, provider, error, and status data, and where are carefully namespaced Vex Code attributes still unavoidable?

## Answer in brief

Model each Vex Code provider turn as one end-to-end **`invoke_agent` client span**, named `invoke_agent {gen_ai.agent.name}`, from dispatch until the final response is received or the turn terminates. Use `gen_ai.operation.name=invoke_agent`, `gen_ai.conversation.id` for the Vex thread ID, `gen_ai.provider.name` for the actual GenAI provider (`openai`, `anthropic`, and so on), `gen_ai.agent.*` for the coding-agent product, `gen_ai.request.model` for the requested turn model, the agent-span-supported `gen_ai.usage.*` fields for operation-scoped token counts, and the standard error/status rules. Create `execute_tool` child spans only when Vex can bound a real tool execution. Create model inference spans only when Vex can observe a distinct model call; do not fabricate them from turn-level events.

The GenAI conventions do **not** define a turn ID, application/provider routing IDs, an agent-turn lifecycle state, an agent stop reason, cumulative context-window usage, cost, model-reroute details, or references to externally stored content. In addition, some otherwise standard model attributes, including reasoning effort, reasoning-token usage, response model, and compaction, are not part of the current `invoke_agent` span. Those remain application data at the agent-turn boundary and should use a small `vex.*` namespace rather than borrowing `gen_ai.*` names; use their standard `gen_ai.*` forms when a real inference span is available.

This is an adoption of a moving specification, not a stable contract. OpenTelemetry moved GenAI conventions into the dedicated [`semantic-conventions-genai` repository](https://github.com/open-telemetry/semantic-conventions-genai/tree/150760c6252a4bb63c49c9915bad11997d316a15). At the inspected revision, the whole GenAI registry is **Development**, its manifest uses the development schema URL `https://opentelemetry.io/schemas/gen-ai-dev/1.42.0-dev`, and it depends on core semantic conventions 1.43.0 ([manifest](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/model/manifest.yaml), [GenAI overview](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/README.md)). Vex Code should therefore centralise names and mappings behind one adapter and pin the reviewed convention revision/schema rather than scattering string literals through provider drivers.

## Recommended trace shape

```text
invoke_agent Codex                         CLIENT
  gen_ai.operation.name                   invoke_agent
  gen_ai.provider.name                    openai
  gen_ai.agent.name                       Codex
  gen_ai.agent.version                    <if known>
  gen_ai.conversation.id                  <Vex ThreadId>
  gen_ai.request.model                    gpt-5.6-codex
  gen_ai.usage.input_tokens               <per-turn total input>
  gen_ai.usage.cache_read.input_tokens    <per-turn cache reads, if known>
  gen_ai.usage.output_tokens              <per-turn total output>
  vex.turn.id                             <Vex TurnId>
  vex.turn.state                          completed
  vex.turn.reasoning.level                high
  vex.provider.driver.name                codex
  vex.provider.instance.id                codex_work
  vex.provider.turn.id                    <provider-native turn ID, if different>

  execute_tool shell                      INTERNAL
    gen_ai.operation.name                 execute_tool
    gen_ai.tool.name                      shell
    gen_ai.tool.type                      extension
    gen_ai.tool.call.id                   <actual tool-call ID, if known>
    vex.tool.kind                         command_execution
```

The agent convention explicitly separates a remote **client** invocation from an in-process **internal** invocation. Vex invokes Codex, Claude Code, OpenCode, or another coding-agent runtime across a process/protocol boundary, so the client form is the closest match. Its span covers the logical operation, including retries, until the response is fully received, errored, or cancelled; it must not end when `ProviderService.sendTurn` merely returns an acknowledgement ([agent client span](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/gen-ai-agent-spans.md#invoke-agent-client-span), [GenAI span lifecycle](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/gen-ai-spans.md#spans)).

If a future Vex-owned agent executes in the server process, use the `invoke_agent` **internal** span instead. Do not create an `invoke_workflow` span for an ordinary turn: that convention is for a reliably identifiable coordinated process containing multiple agents or other GenAI operations, not a synonym for agent invocation ([workflow span](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/gen-ai-agent-spans.md#invoke-workflow-span)).

## Token and metric cautions

Vex's `ThreadTokenUsageSnapshot` mixes several meanings:

- `lastInputTokens`, `lastCachedInputTokens`, and `lastOutputTokens` can feed the corresponding agent-span `gen_ai.usage.*` fields **only when they describe this turn**. `lastReasoningOutputTokens` uses `gen_ai.usage.reasoning.output_tokens` only on an observed inference span; otherwise it remains `vex.turn.usage.reasoning.output_tokens`.
- `usedTokens`, `maxTokens`, and `totalProcessedTokens` describe active context or cumulative thread usage, not one GenAI operation. They must not be put into operation-scoped `gen_ai.usage.*` fields.
- `cachedInputTokens` may map to `gen_ai.usage.cache_read.input_tokens` only when it really means provider-managed cache reads. A generic application cache count is not equivalent.
- `gen_ai.client.token.usage` is a histogram for a model client operation, split by `gen_ai.token.type=input|output`. Emit it only when Vex can measure an actual inference operation, not from cumulative thread snapshots ([client token metric](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/gen-ai-metrics.md#metric-gen_aiclienttokenusage)).

The current `t3_provider_turn_duration` measures the short `sendTurn` request, so it is not the standard agent duration. The standard `gen_ai.invoke_agent.duration` is specifically an end-to-end **in-process** agent-invocation metric paired with `invoke_agent` internal spans. A Vex remote-agent client turn should use its span duration; if a separate metric remains necessary, keep it Vex-namespaced and define its exact lifecycle ([agent metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/gen-ai-metrics.md#metric-gen_aiinvoke_agentduration)). `gen_ai.execute_tool.duration` is suitable when Vex can bound a real tool execution.

Likewise, do not emit `gen_ai.invoke_agent.inference_calls` unless the provider exposes every distinct model call, and do not count server-side provider tools in `gen_ai.invoke_agent.tool_calls`. Guessing either number produces plausible but false telemetry.

## Content policy

OpenTelemetry says model instructions, inputs, and outputs are large and sensitive, and instrumentations should not capture them by default. Vex Code should implement three modes:

1. **Off (default):** no prompt, output, reasoning, tool arguments, or tool result content in telemetry.
2. **Opt-in buffered:** redacted/truncated final content in the standard structured attributes. Where the SDK cannot represent structured span attributes, serialise valid JSON on the span; events/logs should retain structured form.
3. **External storage:** content in a separately secured store with references on the span.

The current specification explicitly leaves a common attribute for external-content references as a TODO. Streaming chunks are also still a TODO. Therefore external references and any capture/redaction metadata necessarily remain Vex-specific for now ([content guidance](https://github.com/open-telemetry/semantic-conventions-genai/blob/150760c6252a4bb63c49c9915bad11997d316a15/docs/gen-ai/gen-ai-spans.md#capturing-instructions-inputs-and-outputs)).

## Status and cancellation rules

Keep OTel span status and the Vex domain state separate:

- `completed`: span status unset; `vex.turn.state=completed`.
- `failed`: span status `Error`; `error.type` set; `vex.turn.state=failed`.
- user-requested `cancelled`: record `vex.turn.state=cancelled`. Leave OTel status unset when cancellation is expected control flow; set `Error`/`error.type=cancelled` only when cancellation means the instrumented operation failed in its caller contract.
- `interrupted`: record `vex.turn.state=interrupted`. A crash, transport loss, or unrecovered provider exit is an error; a transient interruption that is retried and ultimately completes is not an error on the logical operation.
- `stopReason` values such as `end_turn`, `max_tokens`, `refusal`, or `cancelled` remain `vex.turn.stop_reason` unless they came directly from a particular model generation. A completed-but-truncated or refused agent turn is not automatically an instrumentation/runtime failure.

This follows the core rule that handled/retried errors should not be recorded against a logical operation that completes successfully, while terminal errors should set both status and `error.type` ([recording errors](https://github.com/open-telemetry/semantic-conventions/blob/v1.43.0/docs/general/recording-errors.md)).

## Minimal unavoidable `vex.*` vocabulary

Use standard fields whenever their meaning is exact. For the remaining product concepts, define and test one small vocabulary:

| Attribute/event                                                             | Purpose                                                                                                                                                                                                      |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `vex.turn.id`                                                               | Canonical Vex TurnId; no OTel GenAI turn-ID attribute exists.                                                                                                                                                |
| `vex.turn.state`                                                            | Final Vex lifecycle state: `completed`, `failed`, `interrupted`, or `cancelled`. Pending/running transitions should be events, not an attribute repeatedly overwritten.                                      |
| `vex.turn.stop_reason`                                                      | Provider/agent-level stop reason that is not a model generation finish reason.                                                                                                                               |
| `vex.turn.reasoning.level`                                                  | Requested reasoning effort when Vex has only an agent-turn span; use `gen_ai.request.reasoning.level` on a distinct inference span.                                                                          |
| `vex.turn.usage.reasoning.output_tokens`                                    | Turn-aggregated reasoning tokens when no model inference span exists.                                                                                                                                        |
| `vex.turn.conversation.compacted`                                           | Positive compaction indicator at the agent-turn boundary; use the standard `gen_ai.conversation.compacted` on inference spans.                                                                               |
| `vex.turn.cost.usd`                                                         | Provider-reported turn cost; current GenAI conventions contain no cost/currency attribute.                                                                                                                   |
| `vex.provider.driver.name`                                                  | Driver implementation (`codex`, `claudeAgent`, etc.); distinct from `gen_ai.provider.name`.                                                                                                                  |
| `vex.provider.instance.id`                                                  | User-configured routing instance; never misuse `gen_ai.agent.id`.                                                                                                                                            |
| `vex.provider.thread.id`, `vex.provider.turn.id`, `vex.provider.request.id` | Provider-native correlation identifiers when distinct from canonical Vex IDs. Add only those useful for diagnosis.                                                                                           |
| `vex.tool.kind`                                                             | Vex canonical lifecycle item type (`command_execution`, `file_change`, `mcp_tool_call`, etc.), alongside the much coarser standard `gen_ai.tool.type`.                                                       |
| `vex.thread.context.used_tokens`, `.max_tokens`, `.total_processed_tokens`  | Context-window/cumulative thread values that are not per-operation GenAI usage. Keep these off metric labels.                                                                                                |
| `vex.content.input.ref`, `vex.content.output.ref`                           | References to externally stored content until OTel defines a common reference representation.                                                                                                                |
| `vex.content.capture.mode`, `vex.content.redacted`, `vex.content.truncated` | Auditable handling metadata for opt-in content capture.                                                                                                                                                      |
| `vex.model.rerouted` event                                                  | Requested-to-resolved model changes when there is no distinct inference span on which request/response model attributes can express the change. Include only model identifiers and a low-cardinality reason. |

Do **not** invent new `gen_ai.*` attributes. OpenTelemetry's naming guidance specifically advises application developers not to place custom fields in existing semantic-convention namespaces because future standard names may clash. It recommends an application-specific namespace where no standard exists ([naming guidance](https://github.com/open-telemetry/semantic-conventions/blob/v1.43.0/docs/general/naming.md#recommendations-for-application-developers)). Names should be lowercase, dot-namespaced, and use underscores inside multi-word components.

## Adoption sequence

1. Add a single Vex-owned constants/mapping module pinned to the reviewed GenAI development schema/revision.
2. Introduce the true asynchronous `invoke_agent` lifecycle span; leave the existing short dispatch instrumentation separately named.
3. Map provider, agent, conversation, request model/reasoning, terminal state, error, and per-turn token data.
4. Add event-derived `execute_tool` spans only for tool types with reliable start/end correlation, avoiding duplicates with native MCP/provider instrumentation.
5. Keep content capture off. Add schema-valid buffered capture only behind explicit configuration and redaction tests.
6. Add standard GenAI metrics only where Vex measures the exact standard boundary; retain clearly documented `vex.*` metrics for Vex-specific boundaries.
7. Add fixture tests for Codex and Claude mappings, especially provider identity, Anthropic cache-inclusive input totals, terminal state/error classification, and cumulative-versus-per-turn token separation.
